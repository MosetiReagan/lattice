# Request admission and scheduling

Implemented: one active request with a bounded queue, queue deadlines, output limits, overload 429 responses, cancellation cleanup and priority 0–3 with FIFO tie-breaking and aging. `scheduler/fair.py` explicitly handles cancellation both while waiting and immediately after ownership handoff so reservations cannot leak. Long-waiting lower-priority work can overtake newer high-priority work through aging.

One-slot mode retains non-preemptive admission and explicit model switching. Two-slot mode now delegates continuous token batching to llama.cpp, pins one model and admits two active requests. Each request owns a native slot and private stream session, and a cancelled stream is not recycled until native idle is verified. A single long request no longer blocks all short work; when both slots are occupied, priority/aging apply to waiting work rather than preempting active generations. See concurrent_serving.md for constraints, failure/draining semantics and CPU evidence.

Concurrency/mixed workloads report queue wait, TTFT, total latency and completion/failure counts. The frozen standard snapshot uses FIFO asyncio.Lock; the new priority queue needs independent mixed/priority stability validation before release. P99 is not reported for 30-trial runs. No mocked test is accelerator or production-throughput evidence.

Final race testing found and fixed a cancellation edge: a cancelled future could be removed by release() before its acquire() handler ran, incorrectly looking like a granted handoff. Waiters now track an explicit granted flag. The regression test exercises that exact interleaving and verifies that the new owner retains the lock. The serial adaptive experiment predates this fix (no queued cancellation occurred in that workload); its exact hashed source is preserved in the historical experiment archive, separate from the tested current serving build.
